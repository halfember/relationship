# 联系人添加策略调整方案

## 1. 背景

当前产品存在三套“人”的数据：

- `Relationship`：用户私人的联系人、标签、备注、重要日和回忆。
- 双人 `SharedSpace`：两位注册用户共同维护的空间，每位用户仍保留自己的私人 `Relationship`。
- 家庭 `SpaceMember`：家庭空间成员，允许只有档案、尚未注册。

现状能够覆盖私人记录、双人协作和家庭档案，但入口和创建后的行为不一致：部分入口直接进入手动表单；生日不会自动成为重要日；家庭成员与私人联系人无法关联；同名联系人可以无提示地重复创建。

## 2. 产品原则

统一采用以下策略：

> 添加任何重要的人，先建立一份当前用户可控的私人关系档案；邀请和共同空间是关系的协作升级，家庭身份是可关联的空间角色。

具体原则：

1. 私人关系先行。用户无需等待对方注册即可获得记录与提醒价值。
2. 添加意图先行。所有入口先区分手动记录、邀请共同记录、接受邀请。
3. 最小必填。姓名与关系必须主动填写或选择；生日、标签、备注选填。
4. 时间价值即时建立。填写生日时自动创建年度生日重要日，默认提前 7 天、1 天和当天提醒。
5. 逐步完善。联系人保存后明确提供添加重要日、记录回忆、邀请一起记录三个下一步。
6. 不静默重复。同一用户已有同名联系人时，创建前提示用户确认。
7. 私人数据不因邀请而公开。备注、标签、私人提醒、私人回忆和 AI 记录不进入共同空间。

## 3. 目标流程

```text
添加联系人
├─ 手动添加联系人
│  ├─ 姓名（必填）
│  ├─ 关系（必须主动选择）
│  ├─ 生日（选填，自动生成年度重要日）
│  ├─ 标签、备注（选填）
│  └─ 创建完成
│     ├─ 添加重要日
│     ├─ 记录回忆
│     ├─ 邀请一起记录
│     └─ 暂时完成
├─ 邀请一起记录
│  ├─ 选择已有联系人，或创建新的私人联系人
│  ├─ 创建待接受双人空间
│  └─ 接受后双方各自保留私人称呼和关系类型
└─ 输入邀请码
   └─ 接受双人或家庭空间邀请
```

## 4. 数据规则

### 4.1 私人联系人

- `name`：1 至 32 字，必填。
- `type`：家人、朋友、恋人、同事、同学、其他，必填且由用户主动选择。
- `birthday`：选填。
- `tags`：选填，去重保存。
- `remark`：选填，最多 200 字。

### 4.2 生日同步

联系人生日与生日重要日保持一对一语义：

- 创建联系人并填写生日：同一事务创建标题为“生日”的 `Event`。
- 生日事件：`repeatType = 每年`，`remindDays = [7, 1, 0]`。
- 更新联系人生日：同步更新生日事件日期。
- 首次补充生日：创建生日事件。
- 不通过姓名猜测生日，不生成虚构日期。

首版通过同一联系人下标题为“生日”且按年重复的事件识别系统生日事件。第二阶段增加明确的 `eventType` 字段，消除标题语义依赖。

### 4.3 重复策略

首版采用柔性提示，不做数据库硬拦截：

- 前端对同一用户下标准化后同名联系人进行提示。
- 用户可以确认继续创建，以支持同名家人、同事等真实场景。
- 第二阶段增加合并工具，不直接删除或覆盖已有记录。

### 4.4 双人空间

- 从已有联系人发起邀请时，绑定该 `Relationship.sharedSpaceId`。
- 直接发起邀请时，先为发起人创建私人联系人。
- 接受者接受后，为接受者创建自己的私人联系人。
- 双方私人称呼和关系类型互不覆盖。
- 邀请过期、撤回或解除空间时只解除关联，私人联系人保留。

### 4.5 家庭成员

第一阶段继续使用 `SpaceMember`，不与 `Relationship` 自动合并，避免未经确认复制或覆盖数据。

第二阶段新增显式关联：

- 为私人联系人增加可选的家庭成员引用，或建立独立 `PersonLink`。
- 关联前展示双方字段差异，由用户决定生日、头像、称呼的主数据来源。
- 一个家庭档案绑定注册账号后，不自动公开该账号的私人联系人数据。

## 5. 分阶段实施

### 第一阶段：统一创建闭环

- [x] 输出策略文档。
- [x] 所有“添加联系人”入口统一展示三种添加意图。
- [x] 手动创建取消默认关系，要求主动选择。
- [x] 同名联系人创建前提示确认。
- [x] 生日自动创建年度重要日和默认提醒。
- [x] 联系人创建成功后展示下一步操作。
- [x] 增加服务端事务与自动生日事件测试。

### 第二阶段：统一“人”的身份

- [ ] 设计 `Relationship` 与家庭 `SpaceMember` 的显式关联模型。
- [ ] 提供重复联系人识别与合并工具。
- [ ] 为事件增加 `eventType`，明确区分生日、纪念日与自定义事件。
- [ ] 建立头像、生日等字段的来源与冲突解决规则。
- [ ] 编写历史数据迁移和回滚方案。

### 第三阶段：提高添加质量

- [ ] 支持联系人头像。
- [ ] 支持从微信分享卡片或通讯录授权场景快速填充（遵循平台权限）。
- [ ] 根据关系类型提供可选的后续字段，不扩大首屏必填项。
- [ ] 增加添加入口、完成率、生日填写率和后续动作转化埋点。

## 6. 第一阶段验收标准

1. 首页、联系人页空状态和联系人页加号进入相同的添加意图菜单。
2. 用户未选择关系时不能保存，页面不给出隐式默认值。
3. 已有同名联系人时出现确认提示，取消不会提交，确认后允许创建。
4. 填写生日后，联系人详情立即显示一条年度“生日”重要日。
5. 创建联系人与生日事件任一步失败时，二者都不落库。
6. 创建完成后可以直接添加重要日、记录回忆或邀请共同记录。
7. 未填写生日时不创建生日事件。
8. 服务端类型检查、构建和自动化测试通过。

## 7. 不在第一阶段处理

- 自动合并现有家庭成员和私人联系人。
- 自动读取微信好友或系统通讯录。
- 用姓名判断是否为同一个真实人物。
- 自动把私人记录同步到共同空间。
- 删除历史重复联系人。
